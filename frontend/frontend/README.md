# VVSPEC — Robot Observatory

Frontend для мониторинга роботов, локальных траекторий и проблем. React + TypeScript + Vite; TanStack Query, Dexie, Zod, Recharts, React Hook Form. Backend и симулятор не входят в приложение.

## Быстрый запуск

Требуется Node.js 22.12+ и npm. В каталоге frontend:

```sh
npm ci
cp .env.example .env
npm run dev
```

В PowerShell вместо `cp` можно использовать `Copy-Item .env.example .env`.
Откройте адрес, напечатанный Vite (обычно http://localhost:5173).
Backend должен быть доступен отдельно. Если он недоступен, приложение покажет ошибку и ранее сохранённые данные; оно не подставляет демонстрационные значения.

```env
VITE_API_BASE_URL=http://localhost:8000
VITE_WS_BASE_URL=ws://localhost:8000
VITE_TELEMETRY_HISTORY_LIMIT=50000
VITE_DEFAULT_WINDOW_SECONDS=600
```

URL задаются только в модуле конфигурации, проверяются Zod. При отсутствии переменных используются значения из примера. Неправильная конфигурация выводится отдельным экраном. Лимит истории: 100–50000 точек, период по умолчанию: 10–86400 секунд. Перезапустите Vite после изменения переменных. Значения VITE_* публичны и попадают в браузер — не помещайте туда ключи и секреты. Реальный .env исключён из Git.

## Подключение

Приложение читает только существующие методы:

- GET /api/robots и /api/robots/{robot_id};
- GET /api/robots/{robot_id}/telemetry и /telemetry/latest;
- GET /api/robots/{robot_id}/trajectory;
- GET /api/robots/{robot_id}/metrics и /metrics/timeseries;
- GET /api/robots/{robot_id}/events;
- WebSocket /ws/live?robot_id=... .

Клиенты для всех методов присутствуют. Основной экран использует список роботов с последней точкой, историю, траекторию, метрики, временные метрики и события; отдельные one/latest не дублируют эти запросы. Клиент никогда не отправляет прикладных WebSocket-сообщений. Только GET-запросы: закрытие проблемы не вызывает HTTP-запрос.

Периоды — скользящие, до текущего времени компьютера. Сводки и события обновляются каждые 15 секунд, live-телеметрия — пакетами до 5 обновлений UI в секунду. Карта показывает метры в локальной системе координат, не географию. Поддерживает автоматическое вписывание, zoom и следование. При pose=null маркер остаётся в последней известной позиции. На графиках есть легенды, единицы и tooltip. Для графиков используется до 1000 точек, карты — до 3000, только на этапе отрисовки.

## Защита телеметрии

1. При выборе робота старая сессия закрывает WebSocket, отменяет запросы и таймеры.
2. Сначала загружается его IndexedDB-кэш. Данные других роботов сохраняются.
3. Фиксируется начальный диапазон; история, траектория, сводки и события загружаются через REST.
4. После начальных запросов открывается WebSocket. После открытия выполняется дополнительный REST catch-up.
5. Live-сообщения принимаются и сохраняются даже во время catch-up. Объединение сортирует точки и удаляет дубликаты по timestamp_ms.
6. При обрыве массив не очищается. Переподключение: 1, 2, 4, 8, 15, 30 секунд с jitter ±15%, максимум 30 секунд.
7. После восстановления выполняется catch-up; каждые 15 секунд происходит дополнительная REST-сверка, в том числе после её предыдущей ошибки.
8. При одинаковом timestamp_ms входящая версия заменяет сохранённую. Порядок поступления версий детерминирован; входные массивы не мутируют.
9. IndexedDB хранит последние N точек каждого робота и атомарно обновляет timestamp последней сохранённой точки. Самые старые точки удаляются в той же транзакции.
10. Отдельная отметка syncedThrough хранит timestamp последней подтверждённой REST-точки. Это не время окончания запроса: пакет с более ранним временем может попасть в базу backend позже снимка REST. Catch-up повторно включает последнюю подтверждённую точку. Live-пакет эту отметку не продвигает. При перезагрузке после неудачного catch-up пропущенный интервал запрашивается снова. При ошибке сохранения эта отметка также не продвигается.
11. После ошибки записи следующая попытка сохраняет весь оставшийся буфер, а не только новый пакет.

Ограничения: backend может прореживать ответы при более чем 50000 точек (stride > 1). В интерфейсе остаётся явное предупреждение; обещать полное восстановление такого диапазона нельзя. API не предоставляет курсорной пагинации. Лимит локальной истории намеренно удаляет старейшие точки. Старые точки, добавленные сервером задним числом до успешно сверенного диапазона, не гарантируются: для строгой доставки нужен серверный sequence/cursor. Системные часы frontend и backend должны быть согласованы.

## Локальное хранение

Dexie управляет базой vvspec-observatory:

- points — ключ [robotId, timestamp_ms];
- cursors — последний timestamp, syncedThrough и признак прореживания;
- issues — события со статусом закрытия;
- preferences — робот, период, тема;
- snapshots — последние ответы списка роботов и аналитических блоков.

Компоненты обращаются к hooks и репозиториям, не к IndexedDB. localStorage не используется. Статусы можно перенести на сервер, заменив IssueStatusRepository.

Закрытые задачи не удаляются автоматически. Список отображается порциями по 20 элементов. Телеметрия ограничена N точками на каждого робота; события сохраняются для истории закрытия, поэтому архив задач со временем занимает место. При исчерпании квоты появляется ошибка. Данные браузера привязаны к origin (протокол, хост, порт): используйте один адрес frontend. Очистка данных сайта удаляет кэш и статусы. IndexedDB не является резервной копией: очистка браузером, режим инкогнито или сбой диска не позволяют гарантировать долговечность. Данные становятся сохранёнными после завершения асинхронной транзакции; при аварийном закрытии вкладки незавершённый пакет восстанавливается через REST, пока он доступен на сервере.

## Проблемы и идентификация

ID — каноническая JSON-запись кортежа [robot_id, type, start_ms, end_ms, message]. Это детерминированный идентификатор без коллизий хэша, учитывающий null отдельно от пустой строки.

Каждый checkbox немедленно обновляет интерфейс. Запись в IndexedDB сохраняет resolved и resolvedAt. Неудачная запись откатывает изменение и показывает ошибку. Повторное получение того же события сохраняет статус. Есть поиск, тип, открытые/закрытые и сортировка; открытые всегда впереди.

**Ограничение API:** backend вычисляет события для запрошенного периода. У продолжающегося события или события на границе скользящего окна могут измениться start_ms/end_ms. По требуемому составу ID оно становится другой задачей; старая остаётся в истории. Без стабильного серверного event_id невозможно безопасно отождествить такие события и переносить закрытие автоматически. Новое событие оставляется открытым. Серверных операций изменения статуса нет.

## Структура

```text
src/
  app/                 # приложение, providers, QueryClient
  api/                 # fetch, AbortController, Zod, API-методы
  config/              # окружение, интервалы и лимиты
  db/                  # Dexie и адаптеры хранения
  entities/            # типы, схемы, ID, merge и преобразования
  features/            # выбор робота, live-сессия, список проблем
  widgets/             # header, карта, движение, метрики, графики, задачи
  pages/dashboard/     # композиция основного экрана
  shared/              # состояния UI, hooks, числа, даты, тексты
  test/                # unit/integration/RTL и сетевые MSW-тесты
e2e/                   # браузерная проверка на перехватываемом API
```

Одна страница не требует router. Time-range встроен в Dashboard, все настройки сохраняются через общий hook. CSS использует одну систему обычных классов и переменные темы. Русские пользовательские тексты собраны в shared/lib/ru.ts для будущей локализации.

## Ошибки и диагностика

- **Backend недоступен:** проверьте VITE_API_BASE_URL и запуск своего сервера. Сохранённые данные не очищаются, REST-запросы повторяются.
- **CORS:** разрешите origin frontend в конфигурации существующего backend или настройте свой reverse proxy. Frontend не может обойти CORS. Браузер не позволяет отличить его от части сетевых ошибок; проверьте вкладку Network.
- **Неверный URL:** модуль Zod укажет неправильную переменную. Для опубликованного HTTPS frontend нужен HTTPS backend.
- **WebSocket не подключается:** проверьте VITE_WS_BASE_URL, путь /ws/live и поддержку Upgrade прокси. На HTTPS странице используйте wss://. Приложение показывает переподключение и продолжает REST-сверку.
- **Нет роботов:** GET /api/robots вернул пустой список. Роботы должны появиться в существующем backend.
- **Нет телеметрии:** робот зарегистрирован, но точки ещё не пришли либо выбран слишком короткий период.
- **404:** сообщение различает robot not found и no telemetry yet.
- **422:** backend отклонил параметры диапазона; проверьте часы и контракт API.
- **500:** серверная ошибка видна в соответствующем блоке; старые данные остаются.
- **Невалидный JSON/схема:** ответ отклоняется. Некорректный WebSocket-пакет показывает предупреждение и запускает REST-сверку.
- **IndexedDB недоступна:** проверьте разрешения сайта, инкогнито, свободное место. Телеметрия продолжает отображаться в ограниченном буфере памяти; checkbox откатывается, если не сохранён. Между перезапусками несохранённые данные недоступны.
- **Порт frontend занят:** Vite предложит следующий. Чтобы сохранить прежний origin и кэш, освободите исходный порт; либо запустите npm run dev -- --port 5174 и учтите отдельное хранилище.
- **Телеметрия устарела:** свежесть рассчитывается по timestamp точки, а доступность backend и WebSocket отображаются отдельно.
- **Сборка:** npm run build, затем npm run preview. Настройте HTTP-сервер статических файлов для каталога dist.

## Проверки

Vitest покрывает идентификаторы, преобразования, дедупликацию/сортировку/лимит, pose=null, backoff, IndexedDB, восстановление закрытия, повторные события, checkbox и откат, загрузку/пустоту/ошибки, HTTP/JSON/схемы/таймаут/отмену, обрыв и REST-catch-up. Сеть в этих тестах перехватывает MSW.

Браузерные тесты используют тестовые перехватчики Playwright, проверяют заполненный dashboard, WebSocket-обновление, сохранение закрытия после reload, мобильную ширину и ошибки подключения. Рабочая production-сборка никогда не запускает mock по умолчанию.

Для настоящей интеграции требуется работающий backend по указанным URL. Никакие изменения backend и симулятора для сборки frontend не нужны.
